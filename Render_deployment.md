# Render Deployment Plan

## Goal

Deploy the Spring Boot backend on Render, use Render Postgres for the database, and use Cloudflare R2 for object storage.

## 1. Prepare Cloudflare R2

### Create the bucket

Create one private R2 bucket for application images, for example:

- `sitepulse-images`

This bucket name must match the runtime value of:

- `STORAGE_DEFAULT_BUCKET`

### Create API credentials

In Cloudflare R2, create an access key pair with read/write access to the bucket.

You will use:

- `STORAGE_ACCESS_KEY`
- `STORAGE_SECRET_KEY`

### Determine the R2 S3 endpoint

Use your account-level R2 S3 endpoint:

- `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`

Set this value for:

- `STORAGE_ENDPOINT`
- `STORAGE_PUBLIC_ENDPOINT`

For this codebase, presigned URLs are generated by the backend, so both should point to the R2 S3 endpoint unless you later introduce a separate public hostname strategy.

### Configure the region

Set:

- `STORAGE_REGION=auto`

### Configure CORS on the bucket

If the frontend loads presigned image URLs directly from the browser, configure R2 CORS for your frontend origin(s).

At minimum allow:

- your frontend origin
- `GET`
- headers needed by the browser

## 2. Prepare Render Postgres

Create a Render Postgres database.

Suggested values:

- name: `sitepulse-postgres`
- database: `sitepulse`
- user: `sitepulse`

The app expects the database via:

- `POSTGRES_DSN`

If you use the repo’s existing `render.yaml`, Render can populate this automatically from the database connection string.

## 3. Deploy the Spring Boot App on Render

### Option A: Use `render.yaml` from the repo

The repo already contains:

- `render.yaml`

Recommended flow:

1. Push the repository to GitHub.
2. In Render, create a Blueprint from the repository.
3. Let Render read `render.yaml`.
4. Create the web service and database from that blueprint.
5. Fill in the unsynced secrets in Render before the first real production run.

### Option B: Create the web service manually

Create a Render Web Service with:

- Runtime: `Docker`
- Dockerfile: `Dockerfile`
- Health check path: `/actuator/health`
- Region: same region as the database if possible

The app already binds correctly using:

- `PORT`

## 4. Required Render Runtime Environment Variables

### Required for startup

- `POSTGRES_DSN`
- `STORAGE_PROVIDER`
- `STORAGE_DEFAULT_BUCKET`
- `STORAGE_ENDPOINT`
- `STORAGE_PUBLIC_ENDPOINT`
- `STORAGE_ACCESS_KEY`
- `STORAGE_SECRET_KEY`
- `STORAGE_REGION`

Recommended values:

- `STORAGE_PROVIDER=r2`
- `STORAGE_DEFAULT_BUCKET=sitepulse-images`
- `STORAGE_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com`
- `STORAGE_PUBLIC_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com`
- `STORAGE_REGION=auto`

### Required for actual business functionality

- `OPENAI_API_KEY`
- `DROPBOX_APP_KEY`
- `DROPBOX_APP_SECRET`
- `DROPBOX_REFRESH_TOKEN`

### Required depending on your frontend/runtime setup

- `CORS_ORIGINS`

Set this to the frontend origin or comma-separated origins, for example:

- `https://app.example.com`
- `https://app.example.com,https://admin.example.com`

## 5. Optional Render Runtime Environment Variables

### Usually keep explicitly set

- `OPENAI_MODEL`
- `DETECTION_PROVIDER`

Recommended values:

- `OPENAI_MODEL=gpt-4.1`
- `DETECTION_PROVIDER=openai`

### Optional only if you still want local or alternative YOLO usage

- `PYTHON_YOLO_BASE_URL`
- `YOLO_MODEL_PATH`

For current production intent, these are not needed if you stay on the OpenAI detection path.

### Optional tuning variables

- `STORAGE_PRESIGN_TTL_MINUTES`
- `SYNC_CRON`
- `DETECTION_SWEEP_CRON`
- `ANALYSIS_CRON`
- `MAX_IMAGE_BYTES`
- `CONF_THRESHOLD`
- `PER_CLASS_THRESHOLDS_JSON`
- `MIN_BOX_AREA`
- `ENABLE_ROI`
- `ROI_CONFIG_PATH`
- `BLUR_THRESHOLD`
- `BRIGHTNESS_LOW`
- `BRIGHTNESS_HIGH`
- `SKIP_BAD_QUALITY`
- `MIN_DETECTIONS_ACTIVE_HOUR`
- `DROPBOX_TOKEN`

You can leave most of these at defaults unless you have a reason to tune them.

## 6. Recommended Render Runtime Values

Use this as the practical baseline:

```env
STORAGE_PROVIDER=r2
STORAGE_DEFAULT_BUCKET=sitepulse-images
STORAGE_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
STORAGE_PUBLIC_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
STORAGE_ACCESS_KEY=<R2_ACCESS_KEY>
STORAGE_SECRET_KEY=<R2_SECRET_KEY>
STORAGE_REGION=auto

OPENAI_API_KEY=<OPENAI_API_KEY>
OPENAI_MODEL=gpt-4.1
DETECTION_PROVIDER=openai

DROPBOX_APP_KEY=<DROPBOX_APP_KEY>
DROPBOX_APP_SECRET=<DROPBOX_APP_SECRET>
DROPBOX_REFRESH_TOKEN=<DROPBOX_REFRESH_TOKEN>

CORS_ORIGINS=https://<YOUR_FRONTEND_HOST>
```

And:

- `POSTGRES_DSN` from Render Postgres

## 7. First Deployment Checklist

1. Create the R2 bucket.
2. Create the R2 access key pair.
3. Configure R2 CORS for your frontend.
4. Create Render Postgres.
5. Deploy the Render web service from `render.yaml` or manually from the Dockerfile.
6. Set all required env vars in Render.
7. Confirm the service becomes healthy at `/actuator/health`.
8. Open `/swagger-ui.html` to verify the app is up.
9. Verify the app can read/write R2 objects.
10. Verify Dropbox sync and OpenAI-powered detection/report flows.

## 8. Manual Decisions Still Required

You still need to choose:

- the final production bucket name
- the frontend origin(s) for `CORS_ORIGINS`
- whether to keep `python-yolo` only for local use or support it elsewhere later
- whether to keep default cron schedules or override them in Render
- whether to migrate existing production objects into R2 before cutover

## 9. Cutover Notes

If this replaces an existing production environment:

1. Migrate the database into Render Postgres.
2. Copy existing object data into the R2 bucket while preserving object keys.
3. Point the new Render service at the migrated database and bucket.
4. Validate presigned image URLs, sync jobs, detection, and reporting before switching traffic.
